# Migration Toolkit - Design

## Problem
Moving customer data out of a legacy system into a new one is where implementations
go wrong: inconsistent formats, duplicates, missing required fields, and records that
point at things that no longer exist. This toolkit makes a migration repeatable,
inspectable, and auditable.

## Scope (v1)
- Two entities: accounts and contacts. A contact belongs to an account.
- Input: CSV exports from a fictional legacy CRM (synthetic data, generated by a seeded script).
- Output: clean records in a relational database, plus a reconciliation report.
- Dry-run mode: runs every step except the write.

## Pipeline
1. Extract: read the CSV files.
2. Map and transform: apply a YAML mapping (source column -> target field -> transform).
3. Validate: apply rules, record the reason for every failure.
4. Deduplicate: merge exact duplicates after normalization.
5. Load: write valid records, accounts first, then contacts.
6. Report: reconciliation summary plus a reject file.

## Transforms
- Dates in mixed formats -> ISO 8601
- State names and abbreviations -> two-letter codes
- Phone numbers -> a single normalized format
- Emails -> trimmed and lowercased

## Validation rules
- Account name is required.
- Contact email is required and must be well formed.
- A contact must reference an account that exists. Otherwise it is rejected (orphan).

## Reconciliation invariant
For each entity: rows_in = loaded + rejected + merged.
Every rejected row carries a reason code. Tests assert this invariant against
synthetic data where the correct counts are known in advance.

## Non-goals (v1)
- No UI, no scheduling, no live source-system connections.
- No claim of production readiness.

## Open questions
- Where the target database runs (decided before the load step is built).

## Definition of done
- One command migrates the sample files.
- The report balances for accounts and contacts, with a reason for every reject.
- Tests pass, and the README explains how to run it.
