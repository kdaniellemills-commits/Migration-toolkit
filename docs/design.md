# Migration Toolkit - Design

## Problem
Moving customer data out of a legacy system into a new one is where implementations
go wrong: inconsistent formats, duplicates, missing required fields, and records that
point at things that no longer exist. This toolkit makes a migration repeatable,
inspectable, and auditable.

## Scope (v1)
- Two entities: accounts and contacts. A contact belongs to an account.
- Input: CSV exports from a fictional legacy CRM (synthetic data, generated by a seeded script).
- Output: clean records in a relational database, plus a reconciliation report.
- Dry-run mode: runs every step except keeping the write.

## Pipeline
1. Extract: read the CSV files.
2. Transform: field-level normalizers in transforms.py (dates, states, phones, emails).
   Empty input returns None, uncleanable input raises ValueError, nothing is guessed.
3. Validate: apply rules, record the reason for every failure.
4. Deduplicate: accounts by source ID, contacts by normalized email. First row wins.
5. Load: one transaction, accounts first, then contacts.
6. Report: reconciliation summary, report.json, and one reject file per entity.

## Reject reasons (first failing check wins)
- Accounts: missing_name, invalid_state, invalid_phone, invalid_date
- Contacts: missing_email, invalid_email, invalid_phone, orphan_account
Duplicates are only detected among rows that passed validation.

## Reconciliation invariant
For each entity: rows_in = loaded + rejected + merged, and every rejected row carries
exactly one reason. The program refuses to load if this does not hold. Tests check the
pipeline and loader against expected.json, whose numbers were fixed when the data was
generated.

## Assumptions
- All-numeric dates such as 03/04/2021 are read as US month/day/year. Ambiguous dates
  are a known migration risk, so this is a deliberate, stated choice rather than a guess.

## Decisions
- Target database: SQLite by default, so the toolkit runs with no setup. DATABASE_URL
  selects another database. Only SQLite is tested.
- The load is one transaction. A dry run performs the inserts and rolls back, so the
  database's own constraints are exercised.
- v1 loads into an empty target. A re-run fails on the unique source-ID constraint and
  changes nothing.
- SQLite foreign keys are enabled explicitly so SQLite and Postgres behave the same.

## Non-goals (v1)
- No UI, no scheduling, no live source-system connections.
- No claim of production readiness.

## Possible next steps
- Move field mapping into a configuration file.
- Incremental loads and upserts.
- Fuzzy duplicate matching.
- Test against Postgres.
